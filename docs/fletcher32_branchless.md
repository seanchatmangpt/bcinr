# Fletcher-32 Branchless Implementation in BCINR

The `bcinr` implementation of the Fletcher-32 checksum (`fletcher32_branchless`) is designed to adhere strictly to the project's constitutional laws, particularly the **$CC=1$ (Radon Law)** and the **Zero-Allocation Boundary**.

## Zero-Allocation Boundary Compliance
The algorithm operates purely on 64-bit unsigned integers (`u64`) passed by value, returning a `u64` result. 
* **No Heap Allocation:** It does not use `Vec`, `Box`, or any heap-allocated collections. All intermediate states (`s1`, `s2`) are stored as fixed-width, stack-allocated scalar values.
* **$O(1)$ Space Complexity:** The memory footprint is strictly bounded and resolved entirely at compile time, guaranteeing zero heap allocations during the hot-path execution and adhering to `#![no_std]` constraints.

## $CC=1$ and Branchless Execution
The $CC=1$ rule mandates that no public primitive shall contain a single `if`, `match`, or data-dependent `loop`. Logic must be expressed as straight-line code to avoid any loop backedges or conditional branches in the final object code.

### Explicit Loop Unrolling
To avoid control-flow hazards and loop backedges, the conventional `for` loop used to process the words (as seen in the test oracle `fletcher32_branchless_reference`) is explicitly unrolled in the authoritative implementation. 

Instead of dynamically iterating over the 64-bit input `val` in 16-bit chunks, the code hardcodes the bitwise shifts and masks for all four 16-bit words sequentially:

```rust
    // Initialization from 'aux' seed
    const MOD: u64 = 65535;
    let mut s1 = (aux & 0xFFFF) % MOD;
    let mut s2 = ((aux >> 16) & 0xFFFF) % MOD;

    // Word 1 (Bits 0-15)
    s1 = (s1 + (val & 0xFFFF)) % MOD;
    s2 = (s2 + s1) % MOD;

    // Word 2 (Bits 16-31)
    s1 = (s1 + ((val >> 16) & 0xFFFF)) % MOD;
    s2 = (s2 + s1) % MOD;

    // Word 3 (Bits 32-47)
    s1 = (s1 + ((val >> 32) & 0xFFFF)) % MOD;
    s2 = (s2 + s1) % MOD;

    // Word 4 (Bits 48-63)
    s1 = (s1 + ((val >> 48) & 0xFFFF)) % MOD;
    s2 = (s2 + s1) % MOD;

    // Packing the final checksum
    (s2 << 16) | s1
```

### Modulo Operations
The modulo operations (`% MOD` where `MOD = 65535`) are applied unconditionally at each arithmetic step. 
* In a typical branching implementation, one might use an `if s1 >= 65535 { s1 -= 65535; }` condition to optimize the modulo reduction. 
* In `bcinr`, this is strictly forbidden. The `%` operator is used outright, delegating to deterministic, branchless instruction sequences generated by the compiler (e.g., multiplicative inverses for constant divisors), ensuring the execution path and timing remain completely independent of the input data values.

By pairing fully unrolled bitwise extractions with unconditional fixed-divisor modulo arithmetic, `fletcher32_branchless` guarantees a mathematically stable, $O(1)$ time complexity execution with zero dynamic dispatch.
