# Rule 7: Whole-Call-Graph Branchlessness

In the BCINR framework, Rule 7 strictly dictates that branchlessness must apply to the *transitive* call graph, rather than merely the public entry point of a function. This requirement is fundamental to maintaining BCINR as a deterministic computational substrate.

## Why Transitive Branchlessness is Required

The primary governing principle of BCINR is that admitted input must pass through a **fixed instruction shape** to produce a **deterministic output**. 

If branchlessness were only enforced at the public API boundary, conditional logic and data-dependent execution paths could easily be hidden in deeper layers of the call stack. This would violate the substrate's absolute runtime laws, including zero data-dependent branches, fixed execution work, and the absence of timing side-channels. A function cannot claim to be branchless just because its immediate source code lacks an `if` statement; if any function it calls (or any function *that* function calls) contains a branch, the determinism of the entire operation is compromised.

To guarantee true fixed-width execution, the structural audit must trace the entire call hierarchy:
`root function → direct callees → transitive callees → compiler intrinsics → linked runtime symbols`

The permitted claim is never "The function contains no `if`, therefore it is branchless," but rather: 
> *"The full authoritative call graph contains no input-dependent conditional branch in the audited release object code for the declared target."*

## How `@turing_machine` Audits Hidden Branches

The `@turing_machine` role (Enforcer of Determinism) holds exclusive authority over structural audits and is responsible for verifying that every authoritative function maintains a cyclomatic complexity of exactly `CC = 1`. This structural audit cannot be bypassed by language abstractions.

Here is how `@turing_machine` enforces transitive branchlessness across various Rust constructs:

### Private Wrappers
Moving conditional logic out of a public function and into a private helper function does not reduce the cyclomatic complexity standing of the authoritative call graph. `@turing_machine` scans all private functions and requires that any private function reachable from an authoritative root strictly adheres to the same `CC = 1` rules. 

### Macros
Macros can easily hide branches, panic paths, or short-circuiting logic behind simple-looking invocations. To combat this, `@turing_machine` does not merely scan the raw source text; it inspects the **parsed syntax tree** and **macro expansions**. Any branch generated by a macro counts as a violation.

### Trait Methods
Because dynamic dispatch is completely prohibited by BCINR's absolute runtime laws, all trait methods must be statically dispatched. However, even with static dispatch, the specific implementations of those trait methods must be structurally lawful. Branches hidden in trait implementations (whether local or from dependencies) count towards the call graph's cyclomatic complexity and will be flagged by `@turing_machine` if reachable at runtime.

### Generic Monomorphizations
Rust's generics allow code to be instantiated differently based on types. `@turing_machine` is responsible for ensuring that the final monomorphized versions of generic functions contain no data-dependent control flow, implicit bounds-check panic paths, or unapproved intrinsics. Because source-level claims do not substitute for object-code evidence, `@turing_machine` relies on exact production-profile disassembly audits to verify that the final object code for every monomorphization is fully branchless.
