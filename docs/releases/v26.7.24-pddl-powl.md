# bcinr PDDL and POWL v26.7.24

## Release law

`v26.7.24` separates two production planning rails rather than rounding partial support into one universal claim.

1. **Witnessed STRIPS composition** uses `PddlPowlRuntime` / `execute_pddl_to_powl`.
   It admits the production STRIPS + typing profile, computes causal independence, projects only witnessed dependence into POWL v2 precedence, executes compatible actions in the same scheduler tick, applies parallel STRIPS state semantics, and emits scheduler plus state-transition receipts.
2. **Exact bounded classical composition** uses `plan_exact_cognitive_workflow`.
   It preserves Boolean conditions, object equality, universal and existential quantification, numeric fluents and effects, conditional effects, and quantified effects. Its POWL 2.0 projection is intentionally sequential unless a separate independence witness exists. It emits a replayable POWL v2 execution receipt.

These rails are complementary. The richer classical rail does not infer concurrency from a serialized plan. The concurrent STRIPS rail does not silently flatten richer PDDL semantics.

## Public usage

### Concurrent witnessed STRIPS

```rust
use bcinr_pddl::execute_pddl_to_powl;

let execution = execute_pddl_to_powl(domain_pddl, problem_pddl)?;
execution.verify()?;

for batch in execution.execution_batches()? {
    println!("simultaneous actions: {batch:?}");
}
```

The returned `PddlPowlExecution` contains:

- the admitted and validated PDDL workflow
- the compiled planner-output POWL v2 tape
- the whole-run POWL v2 scheduler receipt
- the PDDL state-transition receipt
- the final state
- deterministic replay through `verify()`

### Exact bounded classical semantics

```rust
use bcinr_pddl::{
    plan_exact_cognitive_workflow,
    CognitiveProjectionStanding,
};

let workflow = plan_exact_cognitive_workflow(domain_pddl, problem_pddl)?;
assert_eq!(
    workflow.projection_standing,
    CognitiveProjectionStanding::ExactSequential,
);
```

Use `plan_exact_cognitive_workflow_bounded` to supply explicit grounding, plan-depth, and search-state limits.

### Hand-authored POWL 2.0

```rust
use bcinr_powl::powl2::{
    compile_powl2,
    LowestIndexPolicy,
    Powl2Model,
};
use bcinr_powl::scheduler::StableMaximalSelector;
use bcinr_powl::scheduler_v2::execute_v2;
use bcinr_powl::tape::v2::ConcurrencyGuardTable;

let model = Powl2Model::ChoiceGraph {
    children: vec![
        Powl2Model::Activity("start".into()),
        Powl2Model::Activity("left".into()),
        Powl2Model::Activity("right".into()),
        Powl2Model::Activity("end".into()),
    ],
    edges: vec![(0, 1), (0, 2), (1, 3), (2, 3)],
    start: 0,
    end: 3,
};

let compiled = compile_powl2(&model, &mut LowestIndexPolicy)?;
let (state, outcome) = execute_v2(
    &compiled.tape,
    &mut StableMaximalSelector,
    &ConcurrencyGuardTable::empty(),
    64,
);
```

## Admitted semantics

| Surface | Standing | Production rail |
|---|---|---|
| STRIPS add/delete planning | Exact within explicit search bounds | Both |
| Typed grounding and subtype inheritance | Exact | Both |
| Negative preconditions | Exact within explicit search bounds | Exact classical |
| Disjunctive preconditions | Exact within explicit search bounds | Exact classical |
| Object equality and inequality | Exact within explicit search bounds | Exact classical |
| Universal and existential conditions | Exact within explicit search bounds | Exact classical |
| Conditional effects | Exact within explicit search bounds | Exact classical |
| Quantified effects | Exact within explicit search bounds | Exact classical |
| Numeric comparisons and arithmetic | Exact within explicit search bounds | Exact classical |
| Numeric assign/increase/decrease/scale | Exact for admitted, non-conflicting simultaneous updates | Exact classical |
| Causal partial-order recovery | Witnessed under-approximation | Concurrent STRIPS |
| Minimal-nonface concurrency guards | Exact admission/refusal for supplied guards | POWL v2 |
| POWL activity, sequence, partial order, do-redo | Executable | POWL 2.0 |
| POWL 2.0 choice graph | Executable, bounded path selection | POWL 2.0 |
| Scheduler and state replay | Cryptographically receipted | Concurrent STRIPS / POWL v2 |

## Typed exclusions

The exact classical rail refuses the following before producing a plan:

- durative actions and timed initial literals
- PDDL+ processes and events
- continuous effects
- object-valued fluents
- derived predicates
- trajectory constraints
- preferences
- optimization metrics
- conflicting simultaneous numeric updates
- grounding, plan-depth, search-state, tape, or choice-path bound exhaustion

The compatibility temporal grounder remains available outside this production profile. Its existence is not used as evidence that the exact classical rail supports temporal planning.

## Canonical conformance fixtures

The release gates compact instances of the standard planning-domain families used throughout the International Planning Competition and planning literature:

- typed Logistics: load, drive, unload; exact three-step plan and unreachable-route falsifier
- Blocks World: pick-up then stack
- Gripper: pick, move, drop

The POWL gates cover:

- original POWL partial-order execution with independent children firing together
- recursive sequence and do-redo composition
- POWL 2.0 generalized choice graphs with start/end path coverage
- cycle, invalid-edge, off-path-node, tape-bound, and choice-bound refusals
- planner-output POWL v2 compilation, scheduling, receipt sealing, tamper refusal, and replay

Reference lineage:

- POWL: `10.1007/978-3-031-41620-0_6`
- Discovering Partially Ordered Workflow Models: `10.1016/j.is.2024.102493`
- POWL 2.0: generalized choice-graph extension described in the 2026 POWL 2.0 publication

## Verifier ladder

The release CI runs:

1. formatting and clippy over all targets and features
2. focused canonical PDDL/POWL conformance
3. workspace tests on Linux, macOS, and Windows using nightly Rust
4. strict-provenance Miri for `bcinr-mfw-ir`, `bcinr-powl`, and `bcinr-pddl`
5. documentation with warnings denied
6. `cargo-audit` and `cargo-deny`

Superseded workflow runs are cancelled automatically so a stale commit cannot occupy release-gate capacity.
