# Rule 21: Reproducible Generation Pipeline in BCINR

In the BCINR architecture, Rule 21 enforces that all generated authoritative code must be mathematically and structurally deterministic. Generated code serves as an unbreakable bridge between high-level upstream semantic models (like RDF/SHACL ontologies) and downstream fixed-execution mechanics. 

The absolute law for code generation mandates a 4-step reproducibility loop:
`clean generation → digest output → regenerate → verify byte-identical output`

## How `cmca_generated.rs` is Produced Without Fixture-Specific Identifiers
1. **AOT Generation**: The **Slow Rail** operates entirely offline and Ahead-of-Time (AOT), parsing complex Semantic Web data (e.g., `cmca-rdf.ttl`) and outputting rigid, branchless artifacts that the Hot Path can execute blindly.
2. **Environment Isolation**: To fulfill the byte-identical requirement, the code generators are legally prohibited from embedding any environment-dependent variables. The code must **not** contain timestamps, random seeds, temporary file paths, or any identifiers specific to local test fixtures.
3. **Cryptographic Binding (Supply-Chain Seal)**: The output `cmca_generated.rs` is strictly bound to its generation context via BLAKE3 hashing. The hash of the generated byte string is stored as the `generated_payload_digest` inside the generation manifest.
4. **Build-Time Verification**: At build time (e.g., via `verify-generated` Makefile task), the system independently calculates the BLAKE3 digest of `cmca_generated.rs`. If it does not perfectly match the digest embedded in the manifest, the system halts with a hard compile failure, rendering hand-editing impossible.
5. **Subsequent Compliance**: Once perfectly reproduced, the code undergoes the rest of BCINR's gates: `scan-cheats` (anti-cheat verification), `contract-gate` (CC=1 verification), and `audit-object-code` (final disassembly to ensure it translates to branchless machine instructions).

## Structure of `cmca_generation_manifest.json`
The manifest acts as the definitive metadata record that seals the boundary between semantic definitions and deterministic execution. It takes the form of a canonical JSON object:

```json
{
  "digests": {
    "admission_digest": "blake3:494df59a...",
    "formula_registry_digest": "blake3:fc96ee0c...",
    "generated_payload_digest": "blake3:5c3a9ead...",
    "generator_digest": "blake3:a9e09415...",
    "numeric_profile_digest": "blake3:a321b76a...",
    "rdf_digest": "blake3:d41228c3..."
  },
  "dimensions": {
    "F": 10,
    "K": 4,
    "N": 8,
    "Q": 4,
    "leaf_floor_n_max": 8
  },
  "generator_source_order": [
    "../../Users/sac/mfw/tools/cmca-generator/generator.py"
  ],
  "numeric_profile": {
    "precision": 80,
    "q16_16_scale": 65536,
    "rounding": "ROUND_HALF_EVEN",
    "signed_max": 2147483647,
    "signed_min": -2147483648,
    "unsigned_max": 4294967295,
    "unsigned_min": 0
  },
  "schema_version": 1
}
```

### Breakdown of the Manifest Keys:
- **`digests`**: Contains exactly six canonical BLAKE3 digests:
  - `rdf_digest`: Hash of the canonical N-Quads serialized input RDF graph.
  - `generator_digest`: Hash of the generator script's source code.
  - `admission_digest`: Hash of the SHACL validation result.
  - `numeric_profile_digest`: Hash of numerical configurations.
  - `formula_registry_digest`: Hash of formula definitions/floor identities.
  - `generated_payload_digest`: Hash of the exact bytes of `cmca_generated.rs`.
- **`dimensions`**: The rigid semantic dimension bounds used by the artifact (`N`, `F`, `K`, `Q`).
- **`generator_source_order`**: The fixed sequence of generator source files used.
- **`numeric_profile`**: Pre-declared numeric constraints (precision, Q16.16 scaling, and rounding strategies).
- **`schema_version`**: The structural schema version of the JSON manifest itself.
