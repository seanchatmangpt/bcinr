# Petri Net Token Replay Engine

The Petri Net token replay engine in `bcinr` provides a deterministic, branchless verification mechanism to simulate token-flow semantics on a Partially Ordered Workflow Language (POWL) structure. It is designed to verify execution traces (causal receipts) against process models, deriving four primary conformance metrics: Fitness, Precision, Generalization, and Simplicity.

## Core Concepts

The system models execution as a token-passing game over a Petri-net-like graph. Each event in a process trace is encapsulated in a **`PowlReplayFrame`**, representing a single transition firing.

### `PowlReplayFrame`
A frame holds the semantic data for a single step in the replay:
- `node_id` & `node_bit`: Uniquely identify the node being fired (using a 1-hot bitmask).
- `required_tokens`: A bitmask of tokens that *must* be present in the active marking for the node to fire (the pre-set).
- `produces_tokens`: A bitmask of tokens generated by the firing (the post-set).
- `activity`, `ts_ns`, `object_ids`: Metadata tracking the operation, timestamp, and touched objects.

### `PowlReplayVerifier`
The `PowlReplayVerifier` maintains the active state of the token replay. It tracks:
- `enabled_tokens`: The active marking (bitmask of live tokens).
- `replayed`: A bitmask of all unique transitions replayed.
- `fitted`: A bitmask of all successfully fitted transitions.
- `enabled_not_taken`: Transitions that were enabled at some point but not chosen.
- `tape_length`: Total number of events processed.

The engine progresses by feeding frames into `verifier.replay_frame(&frame)`.

## Branchless Firing Mechanics (`CC=1`)

Adhering to the `bcinr` structural laws (e.g., the Radon Law), token replay and Petri-net logic heavily rely on branchless arithmetic operations (`CC=1`) and `#![no_std]` execution without heap allocation.

Under the hood, in `bcinr_logic::models::petri`, the engine uses **`KBitSet`** and **`SwarMarking`** for fixed-width, word-aligned bitset manipulation. Operations like `try_fire()` are executed entirely without conditional branching. 

For example, when `replay_frame` validates a transition, it uses XOR and bitmasking rather than sequential logic:
```rust
// Guard 2: all required tokens must be present — branchless XOR check.
let missing = (self.enabled_tokens & frame.required_tokens) ^ frame.required_tokens;
// If missing != 0, required tokens aren't met.
```
Transitions that successfully fire modify the `enabled_tokens` using bitwise logic to consume required tokens and apply produced tokens.

## Conformance Metrics Calculation

Once a trace is fully replayed, the `finalize()` method computes exact conformance metrics using Q16.16 fixed-point branchless mathematics.

1. **Fitness ($F$)**:
   The ratio of successfully fitted nodes to uniquely replayed nodes. For a perfectly fitted trace, this evaluates to `0x0001_0000` (1.0).
   $$F = \frac{\text{Fitted Nodes}}{\text{Replayed Nodes}}$$

2. **Precision ($P$)**:
   Measures how strictly the model constrained the executed behavior, penalizing transitions that were enabled but never taken ($T_{\text{not\_taken}}$).
   $$P = \frac{N_{\text{unique}}}{N_{\text{unique}} + T_{\text{not\_taken}}}$$

3. **Generalization ($G$)**:
   Estimates how well the model accommodates unobserved variations of the trace. Scaled inversely by the total trace length ($L$).
   $$G = 1.0 - \text{clamp}\left(\frac{N_{\text{unique}}}{L + T_{\text{not\_taken}} + 1}, 0.0, 1.0\right)$$

4. **Simplicity ($S$)**:
   Rates the structural minimalism of the trace path, penalized by unconsumed tokens left active at the end of execution ($T_{\text{active}}$). $K=8$ acts as a smoothing constant.
   $$S = \frac{K}{N_{\text{unique}} + T_{\text{not\_taken}} + T_{\text{active}} + K}$$

Any invalid state encountered during replay (such as missing required tokens or unrecognized nodes) returns a typed `ReplayViolation`, cleanly failing the verification loop.
