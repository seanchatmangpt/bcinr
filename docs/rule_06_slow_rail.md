# Rule 6: The "Slow Rail" and the Non-Authoritative Boundary

In the `bcinr` deterministic substrate, Rule 6 of the `AGENTS.md` constitution strictly classifies all source files and functions into two primary domains: the **Authoritative Runtime** (hot path) and the **Slow Rail** (non-authoritative code). 

Understanding the Slow Rail is critical for maintaining the zero-allocation, branchless guarantees of the core runtime.

## 1. Exact Definition and Constraints of the "Slow Rail"

The Slow Rail encompasses all non-authoritative code responsible for complex, non-deterministic, or computationally unbounded tasks that occur entirely outside the critical execution path. 

According to Rule 6, the Slow Rail performs operations such as:
- **Data Parsing & Validation:** RDF parsing, SHACL validation, artifact serialization.
- **Theorem & Algorithm Discovery:** Certificate derivation, symbolic mathematics, eigenvalue search.
- **Tooling & Orchestration:** Code generation, CLI display, dashboards, benchmark orchestration, test references (independent oracles).

**Constraints:**
- The Slow Rail must **never** be linked into or invoked from the authoritative hot path. 
- Any code generated by the Slow Rail that is intended for the hot path is not exempt from the rules; it must pass all authoritative gates (branchless execution, `CC=1`, zero allocation, object-code verification).

## 2. Why is the Slow Rail Permitted to Branch and Allocate?

The Authoritative Runtime is governed by absolute runtime laws: zero heap allocation (`#![no_std]`), absolute `CC=1` (no branches, no `if`/`match`/`unwrap`), and no unbounded execution loops. These constraints guarantee a mathematically verifiable, constant-time, fixed-width execution environment.

However, tasks like parsing variable-length strings, deriving cryptographic certificates, or dynamically allocating memory for CLI dashboards fundamentally require branching (`if`/`while`/`match`) and dynamic heap memory (`Vec`, `String`, etc.). 

By relegating these necessary but non-deterministic tasks to the Slow Rail, the system isolates complexity. The Slow Rail is permitted to use the standard Rust library (`std`), allocate memory on the heap, and utilize standard control flow, thereby keeping the hot path mathematically pure and strictly bounded.

## 3. The Absolute Boundary Separating the Slow Rail from the Hot Path

The boundary between the Slow Rail and the Authoritative Runtime is absolute and physically enforced at the architectural level:

- **Strict Linkage and Invocation Ban:** The hot path cannot call Slow Rail functions. A branchless public function calling a branching private helper on the Slow Rail is a constitutional violation.
- **Separation of Discovery and Verification (Rule 12):** The hot path is prohibited from performing runtime theorem discovery. The Slow Rail *derives* or *discovers* mathematical witnesses, stability certificates, and parameters (e.g., $G, d, \delta$). The Slow Rail then passes these pre-computed artifacts to the hot path, which only *verifies* them using fixed, bit-parallel, branchless arithmetic.
- **Zero-Allocation Asynchronous Handoffs:** When the hot path needs to send data (like telemetry or execution traces) to the Slow Rail (e.g., for receipt hashing or dashboards), it uses bounded, zero-allocation conduits. For example, `bcinr` employs structures like a `LockFreeMpmcRing` to safely pass event traces from the deterministic hot path to a Slow Rail background thread in ~10ns, entirely shielding the hot path from the variable latency of Slow Rail tasks.
- **Error Mapping:** At the extreme outer edge of the system (the Slow Rail boundary), fixed-width numeric typed refusals (errors) generated by the hot path are safely mapped into standard Rust `Result` adapters for logging and user display.
