# Cheat-Scanner Requirements (Rule 17)

According to the `AGENTS.md` BCINR Deterministic Substrate Constitution, Rule 17 explicitly defines the requirements and operational parameters for the `bcinr-cheat-scanner`. The scanner acts as an uncompromising structural auditor enforcing the project's strict anti-cheat manifesto and absolute runtime laws.

## Operational Requirements

The `bcinr-cheat-scanner` is mandated to perform deep, semantic-level inspection rather than superficial textual analysis. To prevent any form of scanner evasion (as defined in CHEAT-006), it must:

* **Parse the full syntax tree**: The scanner must operate on the parsed Abstract Syntax Tree (AST) rather than raw source lines to understand structural semantics.
* **Inspect macro definitions and expanded output**: It must evaluate macros and their fully expanded code to prevent prohibited branches or operators from being hidden via macro indirection.
* **Scan public and private functions**: Code cannot be exempted by being hidden within private wrappers or helper functions.
* **Scan generated Rust**: Generated code is treated as authoritative code and is subject to the exact same structural laws.
* **Normalize code representation**: The scanner must normalize whitespace, strip numeric separators, normalize comments where required, and detect equivalent hex spellings (e.g., to catch obfuscated magic constants like `0xDEAD_BEEF`).
* **Inspect test references and benchmark targets**: Its jurisdiction includes verification code to prevent "benchmark theater" (CHEAT-008) or circular oracles (CHEAT-002).
* **Pinpoint violations precisely**: It must report the exact file, span, and rule identifier for any violation.

## Reporting Format

Any violation discovered by the scanner must be output using a strict, easily parsed format:

```text
CHEAT[rule-id]: <description>
```

**Example:**
```text
CHEAT[CHEAT-006]: prohibited operator hidden in macro expansion
```

Every single finding generated by the scanner is a fatal error that absolutely **blocks merge**.

## Waivers and Baseline Suppressions

**No baseline suppression may be added without a separately admitted waiver artifact.**

The reason for this policy is rooted in BCINR's core doctrine: the repository does not accept implementations that "merely appear correct." Allowing inline suppressions or standard ignore baselines would permit developers or agents to silence structural gates and bypass constitutional laws (such as `CC=1` or the zero-allocation boundary) without oversight. 

If a specific pattern genuinely requires an exception—such as an admitted target-specific intrinsic (e.g., PDEP/PEXT) or an explicitly tracked deviation—it cannot be swept into a baseline suppression file. It requires a formal, independently certified "waiver artifact" that mathematically justifies the divergence, proves it does not introduce data-dependent branches into the hot path, and formally documents the deviation in the project's permanent verification ledger.
