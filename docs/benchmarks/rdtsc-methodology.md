# rdtsc Methodology — hardware-counter tick tables

How the numbers in `benchmarks/rdtsc_results.md` are produced. Harness:
`crates/bcinr-powl/benches/rdtsc.rs` (single file, `harness = false` binary;
run with `cargo bench -p bcinr-powl --bench rdtsc`). Regenerate before
comparing any number below to a fresh measurement; the committed table is a
snapshot of one run on the host named in its Environment section.

## 1. Counter per architecture

`counter_ticks()` (`rdtsc.rs:29-48`) reads a userspace hardware counter:

- **x86_64**: `std::arch::x86_64::_rdtsc()` (the `rdtsc` instruction).
- **aarch64**: `mrs <reg>, cntvct_el0` via inline asm — the virtual counter,
  readable from EL0. On the measurement host (Apple M3 Max) `rdtsc` does not
  exist, so CNTVCT_EL0 is the surrogate; the harness discloses this in
  `COUNTER_NAME`, which is printed and written into every generated table.
- Any other target: `compile_error!` — the harness refuses to produce numbers
  without a hardware counter.

### 1 GHz calibration

CNTVCT_EL0 ticks at a fixed frequency that is not queried from the kernel.
Instead the harness measures ticks-per-nanosecond directly: a busy loop runs
for ~0.25 s against `std::time::Instant`, and `ticks_per_ns` =
(counter delta) / (wall-clock delta) (`rdtsc.rs:107-119`). On the committed
table's host this yields **1.000 ticks/ns** — the counter runs at 1 GHz, so
one tick = 1 ns and all tick columns read as nanoseconds. Every
nanosecond figure in the table is `ticks / ticks_per_ns` from this run-specific
calibration, never a hardcoded constant.

## 2. Counter-read overhead subtraction

The cost of reading the counter itself is measured, not assumed:
`counter_overhead_ticks(1_000)` (`rdtsc.rs:60-69`) takes 1000 paired reads,
sorts the deltas, and takes the median. That median is subtracted
(`saturating_sub`) from every timed sample (`rdtsc.rs:306`). On the committed
run the overhead measured **0 ticks** (paired reads back-to-back at 1 ns
granularity); on slower-counter hosts this term is nonzero and self-corrects.

## 3. Sample counts and per-op reduction

Constants (`rdtsc.rs:76-77`):

- `SAMPLES = 2_000` timed samples per kernel.
- `WARMUP = 200` untimed executions of the kernel before sampling.

Each timed sample brackets exactly one execution of the kernel's inner loop
(`rdtsc.rs:301-308`):

```text
(k.op)();            // flush, untimed
a = counter_ticks();
(k.op)();            // K inner iterations, timed
b = counter_ticks();
per_op = (b - a - overhead) / K
```

`K` is a per-kernel inner-iteration count (`iters` field): 64 for the emit,
1-frame-chain, and replay kernels, 4096 for the conformance-check and
denial-mask kernels, and **1** for `chain_100_frames_rolling` (the 100-frame
loop *is* one iteration). Reporting is the distribution of the 2000 per-op
values — median, p50, p99 (`percentiles()`, `rdtsc.rs:87-92`) — never a mean.

## 4. Arena-recycling warm-up (the 4090-mark page-fault lesson)

The three `emit_*` kernels share `OcelEmitArena`s created **outside** the
timed closures (`rdtsc.rs:158-160`) and recycled inside the loop:

```rust
if arena.len() >= 4090 {
    *arena = OcelEmitArena::new();
}
```

(`rdtsc.rs:166-204`). This mirrors the steady state of the Divan suite
(`receipt_bench.rs`): recycling at the 4090-entry mark keeps the arena's
backing pages resident so the sample measures `emit` itself. The comment in
the harness names the failure mode a fresh-arena-per-sample design would hit:
**first-touch page faults charged to `emit`**. Any reproduction that allocates
the arena inside the timed region is measuring the allocator, not the kernel.

## 5. Fractional per-op ticks for sub-ns kernels

Kernels faster than the counter granularity (conformance check, denial mask —
median ~0.36–0.39 ticks on the committed run) are resolved by averaging over
K = 4096 inner iterations per sample. The per-op figure is therefore a
**fractional tick count** (`(b − a − overhead) / K` as `f64`), not an integer
counter reading; the full-precision fraction is written to the table (e.g.
`0.35595703125`), and its denominator K is visible in the harness. With
1 tick = 1 ns the quantization floor of a single sample is 1 ns spread over
4096 ops ≈ 0.24 ps resolution; the p99 column still shows the raw tail
(~65–68 ticks for emit, i.e. occasional scheduler/fault interrupts inside a
64-op sample) and should be read as tail exposure, not steady state.

## 6. Auto vs hand sections in `rdtsc_results.md`

The harness writes only between explicit markers in
`benchmarks/rdtsc_results.md` (`rdtsc.rs:393-409`):

- `<!-- BEGIN AUTO: generated by cargo bench --bench rdtsc; do not edit -->`
- `<!-- END AUTO -->`

Everything outside the markers (negative-result notes, hand-written
amendment discussion) survives regeneration byte-for-byte. If the file exists
and is non-empty but lacks both markers, the harness **panics rather than
truncating** — wrap the section in markers once by hand, then rerun. Never
hand-edit inside the AUTO block; edit the harness and regenerate.

## 7. Targets, measured envelopes, and the amendment policy

The targets line at the foot of the generated section distinguishes two
registers:

- **Targets** (from `receipt_bench.rs`): design budgets — emit < 10 ns,
  conformance check < 2 ns, replay < 20 ns/frame, denial mask ~ 1 ns.
- **Measured envelope**: where the hardware actually lands. Where a target is
  physically unreachable it is **amended, not silently missed**: the BLAKE3
  chain budget was originally < 15 ns/frame; the 26.10.08 amendment replaced
  it with a < 500 ns/frame measured envelope, with the physical reason stated
  (each frame hashes 131 bytes = 3 serial BLAKE3 block compressions; hash
  compute is ~100% of per-frame cost).

Every amendment carries a **reopen falsifier**: a concrete rerun condition
that reopens the optimization lane (for the chain: a rerun with
`chain_1_frame_blake3` median < 250 ns/frame). Falsifiers stay unmet until a
committed table shows them met; the 26.10.09 negative result
(reset-free hasher reuse, update-after-finalize — both deltas inside run
noise, reverted) left the amendment standing. Negative results are recorded
as hand-maintained sections (§6), never by editing the generated table.
