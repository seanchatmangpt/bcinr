# Formal Verification and Lean to Rust Mapping in BCINR

The `bcinr` project utilizes Lean to create axiomatic definitions and formal proofs of correctness for system behaviors. These formal models are then mechanically translated into the deterministic, branchless Rust substrate via the **Typestate Pattern** and **Zero-Cost Abstractions**.

A prime example is the `ReceiptSound` formalization, which governs when the system is allowed to perform adaptive state mutations.

## 1. The Lean Formal Model (`lean/ReceiptSound.lean`)

The formal verification for adaptive updates is defined in `ReceiptSound.lean`. It dictates that a system cannot mutate its state adaptively without possessing a fully admitted set of proofs (receipts). 

It defines core structural types for these proofs:
* `ControlState`
* `StabilityCertificate`
* `CertificateReceipt`
* `EnvelopeReceipt`
* `OutcomeReceipt`

### The AdaptiveUpdate Constructor
The sole way to construct an adaptive update in the Lean model is through the `AdaptiveUpdate` inductive constructor:
```lean
inductive AdaptiveUpdate : AdaptiveState → AdaptiveState → Type
  | certified
      {control : ControlState}
      (controlAdmitted : AdmittedControlState control)
      (certificateReceipt : CertificateReceipt)
      (envelopeReceipt : EnvelopeReceipt certificateReceipt.certificate before)
      (outcomeReceipt : OutcomeReceipt)
      (mode : before.mode = LearningMode.certifiedLearning)
      ...
```
This forces the Lean prover to verify that *all* necessary conditions and receipts exist before allowing a mutation. 

### The 5 Required Theorems
The `ReceiptSound.lean` model mathematically proves five critical guarantees:
1. **No unwitnessed mutation** (`adaptive_update_requires_outcome_receipt`)
2. **Frozen means immutable** (`learning_frozen_precludes_update`)
3. **Certificate digest binding** (`changed_control_invalidates_certificate`)
4. **Selection and learning are distinct** (`frozen_selection_does_not_mutate`)
5. **RF/AI reduction with admitted control state** (`rf_ai_reduction_with_admitted_control_state`)

## 2. The Rust Substrate Mapping (`crates/bcinr-cmca/src/allocator.rs`)

The `bcinr` Rust substrate achieves mathematical equivalence to the Lean proofs by leveraging Rust's ownership, lifetimes, and Typestate pattern. The Lean inductive propositions are modeled as actual types and arguments in Rust.

### Typestate Receipt Tokens
The formal proofs translate into corresponding Rust structs (e.g., `AdmittedControlState`, `CertificateReceipt`, `EnvelopeReceipt`, `OutcomeReceipt`, and `CertifiedLearning`). Because these tokens have private constructors, caller code cannot fake them; they must be generated by trusted, bound-checked pipelines.

### The `AdaptiveUpdate` Runtime Constructor
In Rust, the Lean `AdaptiveUpdate` rule is enforced by the function `AdaptiveUpdate::admit_adaptive_update`. Look at its function signature:
```rust
pub fn admit_adaptive_update(
    state: AdmittedControlState,
    cert: CertificateReceipt,
    env: EnvelopeReceipt,
    outcome: OutcomeReceipt,
    temperature: NonNegativeFixed,
    distinguishability: NonNegativeFixed,
    _mode: CertifiedLearning,
) -> Option<Self>
```
Just like the Lean inductive type, Rust **requires** the developer to pass in every single receipt. If you don't have the `OutcomeReceipt` or the `CertifiedLearning` mode token, the code simply will not compile.

### Branchless ($CC=1$) Enforcement
Because the `bcinr` project explicitly mandates deterministic, branchless execution in the hot path, `admit_adaptive_update` must map the Lean validations (such as verifying digest bindings across all receipts) into bitwise operations without a single `if` statement:
```rust
let digests_ok = (((state.digest ^ cert.digest)
    | (state.digest ^ env.digest)
    | (state.digest ^ outcome.digest))
    == 0) as u32;

let ok = temp_ok & dist_ok & digests_ok;

// Branchless return of Option
let outcomes = [None, Some(Self { _mode: core::marker::PhantomData })];
outcomes[(ok as usize) & 1]
```

### Protection Against Unwitnessed Mutation
Finally, mutation functions in the runtime, such as `allocate(...)`, accept the result of this check (`Option<&AdaptiveUpdate<CertifiedLearning>>`). If the proof is missing or invalid, the allocation routine bypasses state mutation branchlessly using masked assignments. This establishes a structural guarantee in the generated assembly that perfectly mirrors the Lean `adaptive_update_requires_outcome_receipt` theorem.
