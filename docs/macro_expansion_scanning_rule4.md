# Rule 4: Macro and Build-Script Scanning in BCINR

In the BCINR determinism constitution, the **`@turing_machine`** role (Enforcer of Determinism) is responsible for ensuring that the authoritative runtime remains completely branchless ($CC=1$, also known as the Radon Law). To accomplish this, the `bcinr-cheat-scanner` must overcome a critical vulnerability in traditional linting: the ability to hide branching logic behind macros or code generation.

## Why Macro Scanning is Necessary

According to the Anti-Cheat Manifesto, **`CHEAT-006` (Scanner Evasion)** strictly forbids hiding prohibited control flow (`if`, `match`, `while`) inside `macro_rules!` definitions, macro invocations, or files generated by build scripts. 

If the scanner only inspected raw, unexpanded source code, an adversary could write an invocation like `branchless_add!(x, y)` that looks structurally safe but secretly expands into a branching `if / else` statement. This achieves superficial textual compliance while violating the mathematical and machine-code branchlessness mandated by BCINR.

## How the Scanner Audits Expansions

To prevent this, the `bcinr-cheat-scanner` Abandons regex in favor of full Abstract Syntax Tree (AST) parsing and expansion analysis:

1. **AST Traversal via `syn`**: 
   The scanner parses the Rust code into a true `syn::File` AST and implements the `syn::visit::Visit` trait. This allows it to recursively traverse semantic nodes exactly as the compiler sees them.

2. **Inspecting Macro Definitions**: 
   The scanner overrides the `visit_item_macro` method to extract the raw token stream of `macro_rules!` blocks. It verifies that no explicit control flow tokens (like `if` or `match`) are being smuggled inside the macro definitions to evade function-level checks.

3. **Hooking the Compiler's Expansion Phase**:
   To guarantee $CC=1$, the cheat-scanner analyzes the **fully expanded output** of macros. It ensures that the final instructional shape—what the compiler actually turns into machine code—is entirely free of hidden branches.

4. **Auditing Build-Script (`build.rs`) Output**:
   Rule 21 states that generated authoritative code is not exempt from runtime laws. Placing non-compliant behavior into files produced by build scripts to bypass standard static analysis is a severe `CHEAT-006` violation.
   * The scanner parses the final, expanded AST of all generated files.
   * If a build script builds strings that eventually compile into prohibited Rust source (e.g., hidden loops or `if` statements), the scanner catches it on the expanded source graph.
   * Failing to configure the scanner to inspect generated code results in a **`CHEAT-010` (Gate Jurisdiction Theater)** violation, immediately failing the build.

5. **Token Normalization**: 
   Before structural analysis, the scanner normalizes whitespace and strips comments. This prevents evasion tactics where an agent might try to split tokens across lines or embed block comments inside macro expansions (e.g., `if /* comment */ condition {`) to disrupt parsing.

By operating on the fully expanded macro streams and generated build outputs, the `@turing_machine` guarantees that no branches or unverified complexity can infect the authoritative runtime's call graph.
