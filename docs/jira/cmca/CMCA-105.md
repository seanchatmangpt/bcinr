# CMCA-105: CI does not verify committed bcinr-cmca generated/ tree matches ontology regeneration

**Type:** Infra / CI Hardening
**Priority:** High

## Summary

crates/bcinr-cmca/src/generated/{case_studies,stability_profile,generalization}.rs carry "GENERATED by ggen sync ... DO NOT EDIT, regenerate from ontology/*.ttl" headers, but no build.rs and no CI step regenerates and diffs this tree against ontology/cmca-rdf.ttl + generator.py, so drift between the committed generated code and its ontology source is possible and currently undetected.

## Context

**UPDATE (same session): investigated, CI step NOT added — real blockers found first.**
The parallel hardening pass tasked with implementing this actually tried to run the
generator and compare its output to the committed tree before adding a CI step, and found
three independent reasons a naive "regenerate and diff" step would fail on every merge:

1. **Wrong default output path.** `generator.py`'s default `out_path` is
   `src/generated/case_studies.rs`, but the real committed file lives at
   `src/generated/consequence_mass/case_studies.rs`. Running with no args silently writes
   a new, wrong file instead of touching the real one.
2. **Real content drift, not just formatting**, once pointed at the correct paths: the
   committed files are rustfmt-formatted (the generator never invokes `rustfmt`, so raw
   output never matches as-is) — but more importantly, raw generator output for both
   `case_studies.rs` and `generalization.rs` ends with three `macro_rules!` blocks
   (`unroll_n_static!`, `unroll_q_static!`, `unroll_k_static!`) that are **completely
   absent** from the committed files. Either the generator gained macro emission after
   these files were committed, or the committed files were hand-trimmed after generation —
   either way, generator and committed tree currently disagree on content, not just style.
3. **`stability_profile.rs` has no generator at all.** `grep -rn
   "stability_profile\|StabilityProfile" ontology/*.ttl generator.py` returns zero matches.
   It's hand-written Rust carrying a `GENERATED... DO NOT EDIT` header it doesn't earn —
   there is no ontology source and no generator code path for it.

**This ticket now blocks on fixing the generator/committed-tree relationship itself**
before a "regenerate and diff" CI gate can mean anything. Acceptance criteria below are
updated to reflect prerequisite work, not just the CI step.

Confirmed absent, not assumed: crates/bcinr-cmca/src/generated/ contains case_studies.rs, stability_profile.rs, and generalization.rs, each with a doc-comment stating it is GENERATED by ggen sync from ontology/*.ttl and must not be hand-edited. There is no build.rs in crates/bcinr-cmca that regenerates this tree at build time. .github/workflows/ci.yml was checked directly and contains no ggen sync, no drift/diff step, and no step that re-runs the generator (ontology/cmca-rdf.ttl + generator.py) and compares output against the committed src/generated/ files.

This means a hand-edit to any file in src/generated/, or an update to ontology/cmca-rdf.ttl without re-running the generator, can silently diverge from what the ontology actually specifies, with no CI signal. This is not a hypothetical: earlier in this same session a MAX_LENS_MAGNITUDE domain constant bug demonstrated concretely how this class of silent inconsistency (a value/derivation drifting from its authoritative source without any check catching it) causes real defects to ship undetected. The generated/ vs ontology drift risk is the same failure shape, in a different location.

## Acceptance Criteria

**Prerequisite (blocks everything else):**
- [ ] Fix `generator.py`'s default output path to target the real committed locations
      (`src/generated/consequence_mass/case_studies.rs`, etc.), not `src/generated/case_studies.rs`.
- [ ] Reconcile the `macro_rules!` divergence: either the generator should stop emitting
      `unroll_n_static!`/`unroll_q_static!`/`unroll_k_static!` (if they were deliberately
      trimmed from the committed files for a real reason — find out why), or the committed
      files should include them (if the trim was accidental drift). Investigate git blame on
      both sides before picking a direction.
- [ ] Either bring `stability_profile.rs` under real generation (add ontology data + a
      generator code path for it) or explicitly descope it from this ticket and remove/correct
      its misleading `GENERATED... DO NOT EDIT` header if it's staying hand-written.
- [ ] Have the generator invoke `rustfmt` on its output (or otherwise match the committed
      formatting), so a diff check compares semantically, not on whitespace noise.

**Once the above holds (generator output byte-matches committed tree for real):**
- [ ] Add a CI step to `.github/workflows/ci.yml` that runs the generator into a scratch
      location and diffs the result against the committed `crates/bcinr-cmca/src/generated/`
      tree, failing the job on any difference.
- [ ] Verify locally that the new step passes (exits green) against the current, unmodified
      committed generated/ tree.
- [ ] Verify locally that the new step fails when one of the generated files is deliberately
      hand-edited, confirming the check actually catches drift; revert the hand-edit before
      merging.
- [ ] Document the regeneration command (`generator.py` usage, correct paths) in the CI step
      or an adjacent README/CONTRIBUTING note.
- [ ] CI step naming should read clearly as a ggen/drift check (e.g. `verify-generated-cmca`)
      so future readers of ci.yml understand its purpose without cross-referencing this ticket.
