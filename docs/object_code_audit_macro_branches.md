# Object-Code Audit and the Hidden Branches of Macros & Generics

In `bcinr`, achieving true branchless execution (the Radon Law, $CC=1$) requires profound strictness. Rule 20 of the BCINR Deterministic Substrate Constitution mandates an exact production-profile disassembly audit. This document explains why source-level constraints are insufficient and why inspecting the final machine code is the only path to guaranteeing algorithmic determinism.

## Rule 20: The Object-Code Audit Mandate

Rule 20 explicitly dictates that every supported release target undergoes an exact production-profile disassembly audit. It requires the inspection of all authoritative root symbols and transitive helper symbols for:
- Conditional jumps
- Loop backedges
- Indirect calls
- Panic and bounds-check symbols
- Allocator symbols
- Floating-point and division instructions
- Unexpected runtime library calls

Source-level cyclomatic complexity (`CC=1`) is deemed necessary but fundamentally **insufficient**.

## How Macros and Generics Hide Control Flow

In Rust, high-level abstractions can easily conceal branching logic from standard source-code analysis tools.

### Macros
Macros perform token replacement and syntax tree generation at compile time. A seemingly simple macro invocation like `process_data!(x)` counts as a single statement to a naive source scanner. However, it can expand into `match` statements, early returns (`?`), or panic paths (like `unwrap()`, `assert!()`, or `panic!()`). Unless the scanner evaluates the fully expanded syntax tree, macro-injected branches remain invisible at the source level.

### Generics and Traits
Rust's generic functions undergo monomorphization, generating a distinct copy of the function for each concrete type. While a generic function `fn compute<T: Transform>(val: T)` may look branchless, the specific trait implementation for `T` might contain complex control flow. Branches hidden inside trait implementations or generic dependencies will completely evade a superficial scan of the authoritative root function.

### Implicit Language Features
Even without explicit macros or generics, Rust implicitly injects control flow branches for safety. Operations like array indexing (`arr[i]`), checked arithmetic, or iteration inherently introduce bounds checks and panic paths. These are invisible `if` statements inserted by the compiler.

## Why Source-Level `CC=1` is Insufficient

Source-level Cyclomatic Complexity solely measures the branching constructs explicitly authored by the developer (`if`, `match`, `while`, `for`). It fails to account for:
1. **Macro Expansions:** The actual code generated by macros.
2. **Monomorphized Logic:** The concrete implementations substituted for generic boundaries.
3. **Implicit Panic Paths:** Language-level safety guarantees like bounds checking.
4. **Compiler Optimizations (or lack thereof):** A source-level bounded loop might not be successfully unrolled by LLVM, leaving loop backedges. Conversely, LLVM might introduce conditional jumps during optimization of supposedly branchless code.

Source code is a request to the compiler; machine code is the reality of execution.

## The Necessity of Production-Profile Disassembly

To strictly uphold the absolute runtime laws of `bcinr`, we must audit the final compiled artifact. Using tools like `objdump` or `cargo asm` on a production profile (release mode) is required to guarantee branchlessness:

* **Conditional Jumps:** Disassembly reveals the raw CPU instructions (e.g., `je`, `jne`, `cmov`). If the compiler inserted a jump for any reason (bounds check, optimization anomaly, trait method branch), it will be caught here.
* **Indirect Calls:** Disassembly exposes dynamic dispatch (vtable lookups), which violates deterministic instruction shaping.
* **Allocator Symbols:** Scanning for `malloc` or allocator symbols guarantees the zero-heap-allocation law is respected even in edge cases.
* **Panic / Bounds-Check Symbols:** Verifies that the compiler statically proved safety and successfully optimized away the implicit panic branches.
* **Loop Backedges:** Confirms that loops have been 100% unrolled into straight-line instructions.

Ultimately, algorithmic determinism and constant-time execution cannot be proven by what is written; it can only be proven by what is executed. Object-code audits bridge the gap between intent and physical CPU execution.
